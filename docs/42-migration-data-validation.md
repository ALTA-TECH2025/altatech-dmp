# 42. 舊平台遷移資料校驗：方法論與用例

> 版本 v0.1 草案（2026-10-21），對應 Issue #53（遷移資料校驗）、#54（原始匯入檔維運規範）；補充 docs/22 §4 的 T2／T3。
> **狀態：方法論與用例待客戶確認；校驗工具尚未實作。** 「現況」欄是 `main` @ `1756efb` 加上 PR #37（個資不入庫）、PR #51（內容雜湊 event_id）的行為；標「實測」的是在 ClickHouse 26.10 跑過的結果。

## 0. 一句話

舊平台資料**用新規則清洗後入庫**。新規則是：個資不入庫、身分轉成客戶 IT 的去識別化 key、事件不重複。入庫後逐層核對以下幾件事，全部通過才開放查詢：

- 每一行都有去處。
- key 對得上。
- 事件條數對得上。
- 除了規則要丟的個資，其他每個欄位的值都和原始資料一致。

## 1. 校驗原則

1. **守恆**：原始檔每一行恰好落入一個去處：入庫、完全重複而去重、隔離、壞行、明確略過。各去處計數加總必須等於原始行數，未歸類 = 0。
2. **預期值由規格獨立算出**：依屬性字典與規則表另寫一份參考實作（不 import 管線程式），對同一份原始檔算出「應該入庫的樣子」，再和 ClickHouse 的實際內容比。管線和參考實作同時寫錯的機率很低（與 docs/41「數字正確性用獨立參考實作比對」同一原則）。
3. **雙向差集**：預期減實際 = 0，且實際減預期 = 0。只比總數，會漏掉「多一筆、少一筆」互相抵銷的情況。
4. **個資只在客戶內網、記憶體內碰**：需要原始 ID、金鑰或原始值的核對（key 重算、FPE 還原、原值反查）在客戶環境跑。報告只輸出計數、比率與代碼化 ID，不輸出原值。
5. **丟掉的也要核對**：被丟的欄位必須正好是規則要丟的。少丟是漏網，多丟是誤判，兩種都算失敗。
6. **失敗要大聲**：任何一條查詢出錯，判定就是「失敗」，不能回空表當成沒有差異（現有 `meta._rows` 失敗回空的寫法，校驗工具不可沿用，見 §6）。
7. **可重跑、自動判定**：每個分片（檔案或日）產出一份報告。同一份輸入重跑，結果必須相同。

## 2. 比對的三方

| 代號 | 是什麼 | 提供者 | 和誰比 | 容許差異 |
|---|---|---|---|---|
| A | 舊平台本身：介面或 Impala 的每事件每日筆數、用戶數 | 客戶／舊平台 | B | < 0.1%，超過要逐事件說明（舊平台遲到資料、導出時點） |
| B | 原始匯入檔：每日約 3.8 GB 的 JSON lines、HDFS 導出 | 客戶 | C | **0**：C 完全由 B 加上規則決定，任何差異都是錯 |
| C | DMP：`events`、`user_prop_log`、`id_map`、隔離區、匯入報告 | DMP | B（經參考實作） | — |

A↔B 驗的是「導出完整」，B↔C 驗的是「清洗正確」。兩段分開判定，才知道差異出在哪一段。

## 3. 六層校驗

### L1 檔案層：每一行都有去處

| 去處 | 條件 | 計數來源 |
|---|---|---|
| 空行 | 去空白後為空 | stage |
| 壞行 | JSON 解析失敗、缺 `type`／`distinct_id`、track 缺 `event`／`time` | 隔離檔（只記行號與原因） |
| 個資 ID 隔離 | 未登入但 ID 像個資、`original_id` 像個資 | 隔離檔 `pii_in_id` |
| track → 事件 | `type = track` | `events`（依 batch_id） |
| track 完全重複 | 同時間、同用戶、同事件、屬性完全相同（#39） | 預期去重數（參考實作）= 暫存行數 − 去重後事件數 |
| track_signup → 綁定 | 匿名 → 登入 | `id_map` |
| profile_*（登入） | 用戶屬性操作 | `user_prop_log`（每個屬性一列） |
| profile_*（匿名） | 匿名用戶屬性 | **現況沒有去處**，待 #43 決定 |
| item_set 等其他類型 | 物品表 | **現況沒有去處**，待決定（入物品表，或明確略過並計數） |

判定：`原始行數 = 空行 + 壞行 + 個資 ID 隔離 + Σ各類型暫存行數`，且每一類型的暫存行數都能在目標表找到對應筆數。另外記錄原始檔的大小與 SHA-256，確保重跑、簽結、刪除針對的是同一個檔案（#54）。

### L2 身分層：key 對得上

| 項目 | 方法 | 通過標準 |
|---|---|---|
| 一對一 | 每個分片：uniq(原始登入 ID) 與 uniq(代碼)，以及 (原始, 代碼) 對的數量 | 三者相等（沒有兩個原始 ID 拿到同一個代碼，也沒有一個原始 ID 拿到兩個代碼） |
| 決定性 | 同一原始 ID 在不同檔、不同日、重跑時的代碼 | 全部相同 |
| 公式一致 | 客戶內網抽樣 1,000 個原始 ID，用客戶 IT 的公式或對照表重算 | 100% 等於 DMP 代碼；若客戶提供對照表，改為全量比對 |
| 匿名原樣 | 匿名 `distinct_id` 的預期集合 vs `events.distinct_id` | 雙向差集 = 0 |
| 綁定 | track_signup 的 (匿名 ID → 代碼) 對數 vs `id_map` 新增 | 相等；匿名事件在 7 天內回填到登入用戶（docs/19） |
| 用戶數 | 每日活躍用戶數，A vs C | < 0.1%；登入用戶 100% 有 `v1_` 代碼（T3） |
| 交易帳號 | 客戶內網抽樣，把 FPE 代碼解回原帳號 | 100% 相等（交易來源才有，舊平台事件中帳號類欄位整個丟） |

### L3 事件層：條數對得上

| 項目 | 方法 | 通過標準 |
|---|---|---|
| 每事件每日筆數 | 以 (正式事件名, 台北日期) 分組，預期 vs 實際 | 每組差異 = 0 |
| 別名轉換 | 舊名轉正式名（`events.yaml` aliases） | 舊名在 C 不存在；舊名筆數全部轉移到正式名 |
| 去重只去完全重複 | 同時間同屬性 → 1 筆；同時間不同屬性、不同時間同屬性 → 各自保留 | 去重筆數 = 參考實作算的完全重複筆數 |
| 重送冪等 | 同一檔載入兩次 | 事件數、金額加總不變（只追加，不虛增） |
| 日界與時區 | 台北 23:59:59.999 與 00:00:00.000 | 分屬兩天；`event_date` 以 Asia/Taipei 計 |
| 對舊平台 | 每事件每日，A vs C | < 0.1%（T2），超過的逐事件說明 |

注意：舊平台把 `$SignUp` 算成事件；DMP 現況只把 track_signup 寫進 `id_map`、不寫 `events`，所以 A↔C 比對時 `$SignUp` 要另外處理（定口徑：DMP 是否也記成事件）。

### L4 欄位層：非個資內容正確無誤

| 項目 | 方法 | 通過標準 |
|---|---|---|
| 逐筆指紋 | 每筆事件的指紋 = SHA-256(正式事件名 \| 毫秒時間 \| 代碼化用戶 \| 依鍵排序的保留屬性 JSON)。預期由參考實作從 B 算出；實際從 ClickHouse 把 `props` 還原成同一格式再算 | 雙向差集 = 0 |
| 屬性集合 | 每筆保留屬性的鍵 = 原始鍵 − 規則要丟的鍵 | 完全相等 |
| 物化欄位 | `symbol`、`side`、`channel`、`amount`、`utm_*`、`platform`、`app_id` vs `props` 原值 | 完全相等 |
| 彙總守恆 | 每事件每日：Σ金額、Σ數量、各屬性非空筆數、列舉屬性的值分布 | 金額精確到分（以 Decimal 計），其他完全相等 |
| 時間 | 毫秒保留；儲存為 UTC，顯示為台北時間 | 完全相等 |
| 用戶屬性 | 套用 set／set_once／increment／unset／append 後的最終用戶屬性 | 與參考實作相等（set_once 不覆蓋、increment 累加、unset 清空；#43） |
| 未分級屬性 | 不在屬性字典的鍵 | 照常入庫，並在報告中列出待分級（新屬性要先分級，docs/28） |

### L5 個資層：沒有漏網、也沒有誤丟

| 項目 | 方法 | 通過標準 |
|---|---|---|
| 樣式掃描 | `events.props`、`raw_legacy`、`user_prop_log`、`id_map`、隔離區、暫存檔，以身分證、手機、Email 樣式掃描 | 0 |
| 名單鍵名 | 字典 drop 類鍵名（不分大小寫、忽略 `$`、點分逐段、巢狀任一層） | 在任何表中都不存在 |
| **原值反查** | 客戶內網：從 B 取出名單欄位的實際值，建成記憶體集合，對 C 全表做字串比對 | 0 命中（不依賴樣式，抓得到樣式抓不到的姓名、地址） |
| 丟棄報告 | 每個被丟的鍵與次數，預期 vs 匯入報告 | 完全相等 |
| 誤判候選 | 不在名單上、但被樣式掃描丟掉的鍵，列出 Top 20，附「被丟筆數／出現筆數」 | 人工逐一確認；確認是誤判的，調整樣式或加例外，並補用例 |

### L6 分析層

沿用 docs/22 §4 的 T4（20 個固定查詢，舊平台介面 vs DMP，差異 ≤ 1%，會話類 ≤ 3%）與 T9（分群成員數）。L1–L5 全部通過後才跑 L6；L6 的差異只可能來自口徑，不會來自資料本身。

規模測試：

- CI：2 萬行合成檔，跑完 L1–L5，沿用 e2e。
- 客戶內網：1 天的真實檔（約 3.8 GB），跑完 L1–L5，並記錄校驗耗時。目標是校驗耗時不超過載入耗時的 2 倍。

## 5. 執行方式

1. **工具**：`backend/migration/validate.py`（待實作，#53）。
   - 輸入：原始檔、屬性字典、規則表。
   - 處理：
     - 參考實作逐行算出預期事件、預期用戶屬性、預期丟棄報告。
     - 把預期結果載入 ClickHouse 臨時表。
     - 用 SQL 做雙向差集與彙總比對。
   - 輸出：報告 JSON，並寫入對帳表。
2. **在哪裡跑**：
   - 測試環境用合成資料（CI 每次 PR 都跑）。
   - 客戶內網用真實檔。需要金鑰或原始值的項目只在內網跑：L2 公式一致、L2 交易帳號、L5 原值反查。
3. **報告內容**：分片、原始檔 SHA-256、規則版本（字典 commit）、各層結果、差異樣本（最多 20 筆，只放代碼化 ID 與行號）、判定。不含任何原值。
4. **頻率**：
   - 歷史資料：每個分片一次。
   - 並行期：每日一次。
   - T0 最終增量：一次。
   - 規則（字典、樣式）改版後，已載入的分片要重跑 L4、L5。
5. **關卡**：分片通過 L1–L5 才開放查詢（docs/22 §3）。失敗的分片不開放，並通知負責人。
6. **客戶簽結**：每個事件抽 20 筆，在客戶內網把原始行（個資欄以遮罩顯示）和 DMP 入庫結果並排呈現，由客戶逐筆確認後簽認。抽樣數由客戶決定。

## 6. 現有程式的落差

| 落差 | 影響 | 追蹤 |
|---|---|---|
| 行數守恆不完整：匿名 `profile_*`、`item_set` 沒有去處，空行不計數 | 有些行入庫後就消失，報告看不出來 | #53、#43 |
| `recon_ok` 只比筆數，且沒考慮去重 | ReplacingMergeTree 合併去重後會誤報；也驗不到內容 | #53 |
| 遷移對帳頁 T5／T6 的 SQL 欄名錯、來源名不符 | **實測** ClickHouse 報 `UNKNOWN_IDENTIFIER`，被 `meta._rows` 吞掉，畫面顯示空表，看起來像「沒有差異」 | #49 第 1 項 |
| `amount` 存 Float64 | 加總會出現浮點誤差 | #44 |
| `null` 與缺欄位分不出來 | 「有填但是空」與「沒填」口徑混在一起 | #48 |
| 登入 ID 正規化未定義 | 大小寫、空白不同的 ID 會被當成不同人 | 待客戶確認（§8 第 2 項） |

## 7. 原始匯入檔（DMP 之外，部署時另訂維運規範，#54）

- 原始匯入檔本身含個資，例如每日約 3.8 GB 的舊平台檔、數據中台匯出檔。DMP 只讀取清洗，**不修改、不刪除原檔**。
- 部署時要訂下列事項：
  - 存放位置：客戶內網或專用 bucket，靜態加密，最小權限。
  - 保留期限。
  - 刪除方式與紀錄：檔名、SHA-256、時間、執行者。
  - 負責人。
  - 中間副本（HDFS 導出、傳輸暫存）適用同一規範。
- **原始檔要等該分片校驗簽結後才能刪**，因為 L2 公式一致和 L5 原值反查都要用到原始檔。建議期限為「簽結後 N 天」，N 由客戶定。
- 選配：DMP 在校驗通過且過了保留期後，自動刪除原檔或搬離暫存區，刪除動作寫入稽核。是否啟用由客戶決定。

## 8. 待客戶確認

1. **判定標準**：B↔C 差異必須為 0；A↔B 容許 < 0.1%，超過要逐事件說明。
2. **登入 ID 正規化**：大小寫、前後空白、前導零是否視為同一人？由客戶 IT 的 key 公式定義，DMP 照做。
3. **key 核對方式**：客戶 IT 提供金鑰，DMP 在內網抽樣重算；或客戶 IT 提供「原始 ID → key」對照表，DMP 做全量比對。
4. **`$SignUp`**：是否也記成 DMP 事件，以便和舊平台事件數直接比對？
5. **匿名用戶屬性、`item_set`**：要入庫，還是明確略過？
6. **簽結抽樣數**：每個事件抽幾筆並排核對。
7. **原始檔保留期限與刪除責任**；是否啟用 DMP 自動刪除。
