## 2b. 協同工作方式（全員 Claude Team 帳號）

原則：**一個 repo、契約先行、小 PR 每日合併、AI 做第一輪、人做最後把關**（docs/15 §2、docs/16）。每個角色各用 Claude 的方式不同，但都回到同一個 repo 與 issue 看板。

| 角色 | 用 Claude 做什麼 | 工具與進入點 | 產出回到哪裡 |
|---|---|---|---|
| 研發 R1／R2 | 寫程式、測試、修 bug；每個 Story 一個 Claude Code 雲端 session（指定分支、CLAUDE.md／AGENTS.md 規則、收工前驗證指令）；PR 由 Claude 自動審查第一輪，再互審 | Claude Code（claude.ai/code 或 CLI）、GitHub App | PR → main；自測與 CI 全綠才合併 |
| 產品 | 規格書、手冊、教育訓練教材、UAT 案例草稿；需求表落差逐項對照；系統圖狀態更新 | Claude.ai Project（掛 docs/ 當知識）＋ Claude Code 改 `docs/`；Artifact 發佈規格書網頁 | `docs/`、規格書 artifact、手冊 |
| PM | 站會紀錄、風險登錄、進度報告、待確認追蹤表；時程變更影響分析 | Claude.ai Project（掛 docs/31、docs/17 §5a） | `docs/31`、issue 看板、週報 |
| 數據分析師 | 盤點清單、對帳 SQL、差異歸因、golden 口徑對照、分群／標籤規則重建、情境看板設計 | Claude Code 在 repo 內跑 `backend/semantic/compiler/golden.py`、自定義 SQL 沙盒、AI 生成卡片；Claude.ai Project 掛神策文件與 docs/21、22 | `golden.py`、`seed.py`、對帳報表（repo `reports/`）、docs/22 §4 |
| 運維 | Helm values、告警規則、runbook、導出作業腳本、事故分析 | Claude Code 改 `deploy/`、`.github/`；Claude.ai 問 ClickHouse／K8s 操作 | `deploy/`、runbook、監控看板 JSON |

共同規則：
1. **資料不進 Claude**：只用合成黃金資料與 `demo_fill` 的示範資料；神策真資料、客戶名單、密鑰一律不貼進對話或 repo（CLAUDE.md 既有規則：模擬資料不含真實客戶、密鑰只能 secret_ref）。對帳報表只放筆數與差異率，不放明細。
2. **一個 Story 一個 session、一個 PR**：issue 用 Story 模板寫驗收條件；session 指定分支（`<ws>/<issue-id>-<slug>`），收工跑 CLAUDE.md 的驗證指令並把輸出貼進 PR。
3. **契約先改**：`openapi.yaml`、`semantic/*.yaml`、`security/*.yaml` 的變更獨立 PR，產品與分析師可直接審（口徑），研發不夾帶功能。
4. **每日 15 分鐘站會**（PM 主持）：三件事——昨天合併了什麼、今天的 session 開在哪個 Story、卡在哪個待確認項；每週五看 docs/31 §4.3 風險指標。
5. **文件即規格**：docs/ 是唯一來源，規格書網頁與系統圖由腳本產生（`docs/diagrams/build.py`、規格頁產生器）；改完 docs 就重發，不另外維護投影片版本。
6. **知識轉移**：M0 兩天程式導讀由研發用 Claude Code 帶讀（每個目錄 README → 跑自測 → 改一個小 issue）；分析師與運維各認領一個小 Story 實際走一次流程。
7. **Claude 用量與審計**：Claude Team 由 PM 管帳號與用量；session 連結附在 PR 說明（commit 已含 session 連結），回溯誰在什麼情境下改了什麼。

## 3. 挑戰難點

### 3.1 技術

| 難點 | 為什麼難 | 目前處境 | 對策 |
|---|---|---|---|
| 真實資料從未進過系統 | 所有端到端測試都是合成黃金資料；GA360 匯出 schema 版本、神策 70 億筆的欄位品質、數據中台事實表的鍵與時區都只靠文件 | 接入、轉名、對帳邏輯都有，但沒碰過真資料 | M1 先拿 GA4 真樣本與神策 1 個月樣本跑 T1–T2，再談規模 |
| 規模（220 億事件、650 萬 MAU） | 只量過 200 萬用戶 × 300 屬性與 1,000 萬事件；MV 覆蓋率、分片策略、Bitmap 記憶體都沒在 10 億級驗過 | 查詢編譯器會走 MV，但真資料的事件分布可能讓 90% 查詢走 MV 的假設不成立 | M2 用真歷史資料做 10 億基準；不達標就調 MV 與分片，必要時改口徑（例：預設抽樣） |
| 身分整合 | 只接過假 IdP；Entra ID／AD LDAPS 的群組對照、MFA、session 時效都要在客戶環境才知道 | 登入模組有 OIDC＋PKCE、LDAPS、TOTP 三條路 | M0 第一週就接真 IdP；本機帳號只留作緊急後門 |
| 微批 vs 客戶對「即時」的期待 | 第一階段不上 Flink／Kafka，行為事件 5–15 分鐘可查、推送增量 15 分鐘；需求表 C11／E2 標為落差 | docs/23 已說明並獲理解，但 UAT 時容易被拿出來比 | 文件口徑一致（docs/27 需求表）；儀表板與推送頁都標示延遲；第二階段再談即時 |
| K 匿名在小樣本 | K=20 讓小分公司、小標籤值、短窗口的日線整張被抑制（本週做情境看板就撞到） | 政策正確但體驗差 | 待確認 K 值與適用模組；前端已會提示「抑制列」；考慮分組自動合併為「其他」 |
| 營運與監控空白 | 沒有 Prometheus／Grafana、告警、備份演練；控制面 JSON／PostgreSQL 的備援未定 | docs/27 §2 信心「低」 | M3 最小看板、M5 演練；控制面正式用 PostgreSQL（store_pg 已有自測） |
| 前端沒有斷言型端到端測試 | Playwright 只做截圖與流程檢查，沒有在 CI 對真後端跑 | 回歸靠人眼 | M5 前補：登入→分析→存書籤→看板→推送一條主線在 CI 跑 |
