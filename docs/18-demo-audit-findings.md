# Demo 全面檢查：各模組數據流、效能、建模、權限、元事件／用戶表／維度表 — 問題、漏洞與優化結果

> 版本 v0.1（2026-10-15）。檢查對象：原型 v0.4.2（demo）、後端契約（openapi、semantic、security）、docs/02／04／06／09／10。優化後版本：原型 v0.5.0。

## 1. 總表

| # | 面向 | 檢查發現（優化前） | 風險 | 優化（v0.5） | 狀態 |
|---|---|---|---|---|---|
| 1 | 各模組數據流 | 文件有數據流圖，但原型沒有任何頁面呈現「每個模組讀什麼、寫什麼、延遲多少」；資料源健康只在總覽一張卡 | 客戶看不到端到端可觀測性；上線後排障無入口 | 新增「資料流與效能」頁：端到端七段資料流（吞吐／延遲／狀態）、各模組讀寫表、資料品質六指標 | 完成（原型 + `/v1/ops/pipeline`） |
| 2 | 資料處理效能 | 效能目標散在 docs/04、09；原型沒有查詢 P50/P95/P99 對 SLA、快取命中、掃描量、批次耗時、儲存用量 | 無法證明「百億級可用」；容量到頂無預警 | 同頁「查詢效能」（9 類查詢 × P50/P95/P99/SLA/掃描/快取/路徑）、「批次與儲存」（7 個作業、5 個儲存用量、告警規則）；標示兩個已知風險（路徑 P99、漏斗快取） | 完成（`/v1/ops/query-perf`、`/v1/ops/batch-jobs`） |
| 3 | 數據可視化建模 | 只有一個精靈，沒有數據表管理與任務清單；Schema drift 只在備註 | 與神策「數據源管理／數據表管理／數據同步」結構不符，上線後無任務監控入口 | 依神策通用數據接入改為三層：數據源管理（v0.4.2 鑑權）、數據表管理（主鍵／增量欄位／Schema 版本與變更）、同步任務（目標 events／users／維度表／OneID 綁定／標籤；全量／增量／流；日誌、重跑、複製）；精靈改為建立任務（docs/06 §7） | 完成 |
| 4 | 數據權限管理 | 「數據權限」只是規則表；沒有「使用者 × 角色 × 範圍」的指派介面；不能模擬某角色的行級條件 | 範圍靠口頭約定，上線後容易配錯 | 權限中心新增「使用者指派」（角色多選、範圍、到期、SSO 群組、臨時提權標記、撤銷）與「行級規則模擬」（選角色看 WHERE） | 完成（`/v1/iam/assignments`、`/v1/iam/scope/simulate`） |
| 5 | 元事件管理 | 事件字典唯讀；隔離事件無登記動作；無屬性字典、虛擬事件、變更管控、L4 攔截 | 未登記事件永遠在隔離區；屬性型別／敏感等級無人把關；個資可能隨新屬性入倉 | 重做為「元事件管理」：事件 CRUD 抽屜（命名規則、主體、類別、來源、負責人、路徑節點規則、屬性型別與敏感等級、上線檢查、L4 拒絕、變更單、停用）、屬性字典、虛擬事件、隔離區計數 | 完成（`/v1/meta/events*`、`/v1/meta/properties`、`/v1/meta/virtual-events`、`/v1/meta/quarantine`） |
| 6 | 用戶表管理 | 沒有這個頁面；用戶屬性只在篩選器裡出現；OneID 規則只在細查頁的圖 | 分析師不知道屬性來源／更新時間／覆蓋率；OneID 合併策略無處審核 | 新增「用戶表管理」：16 個屬性（來源、更新、敏感、可篩選／分組、覆蓋率）、OneID 規則（7 種識別、優先序、強度、合併策略、合併／拆分統計）、個資防護（L4 清單、偵測規則、DSAR） | 完成（`/v1/meta/user-properties`、`/v1/meta/oneid/rules`、`semantic/user_properties.yaml`） |
| 7 | 維度表與字典（原 Item 表） | 沒有頁面；第一版把 Item 誤當成「帳戶等有自己事件的主體」 | 與神策口徑不一致；帳戶被當成第二種用戶 | 依神策元數據管理改為「維度表／維度字典／虛擬屬性」：維度表以「屬性值 = 主鍵」補充維度、欄位成關聯屬性；字典給值顯示名；帳戶改為客戶的多值 ID（docs/19）| 完成（`/v1/meta/dimension-tables*`、`dictionaries`、`virtual-properties`；`semantic/dimension_tables.yaml`；docs/06 §7.2） |
| 8 | 角色權限管理 | 角色、自訂角色、模組矩陣完整；**漏洞**：分群審批與推送按鈕未檢查權限（任何角色點了都「核准」）；元事件無寫入權限概念 | 原型示範時會被客戶抓到「分析師能核准推送」 | `approve` 需 `segments.a`、推送需 `segments.u`、元事件寫入需 `governance.d`、連線與輪替需 `integration.d`；分析師視角驗證按鈕不出現 | 完成 |
| 9 | 隱碼與 K 匿名 | 欄位隱碼依角色正確；K 匿名只有文字說明 | 小分組可反推個人 | 列為待確認（§3：K=20 門檻與適用模組） | 待確認 |
| 10 | 審計 | 審計事件涵蓋查詢／細查／推送；缺元事件、Item、指派、密鑰讀取 | 治理動作不留痕 | 新增 `meta.event.*`、`item.sync`、`iam.assignment.*`、`secret.accessed`、`batch.rerun`、`ops.alert` | 完成（契約層） |

## 2. 逐模組數據流檢查

| 模組 | 讀 | 寫／輸出 | 檢查結果 |
|---|---|---|---|
| 數據整合 | 來源系統（CDC／批次） | Kafka raw.*、quarantine、lineage、users（映射到用戶屬性） | 連線鑑權已補；**映射到用戶屬性／維度表的回寫路徑**原本未定義，現在在用戶表／維度表與字典頁說明並寫進契約 |
| 元事件管理 | 隔離區統計、query_log（使用次數） | semantic/events.yaml、Collector 白名單、Flink 事件化規則、ga4_mapping 樣板 | 新增；上線＝三處同步生效，變更單審批 |
| 維度表與字典 | 同步任務寫入的 dim_*、字典上傳 | dimensions.yaml（關聯屬性）、ClickHouse dictionary | 以屬性值 = 主鍵關聯；不是主體 |
| 事件／漏斗／留存／路徑 | events L0、MV L1–L3、users、items（dictGet） | 結果快取、audit_log | 一致；路徑全量查詢的成本需 UI 警示（已在效能頁標示） |
| 歸因 | touchpoints（日批）、events | audit_log | 觸點表重算 04:00，窗口 14 天；窗口改大需重算（待確認） |
| 用戶列表／細查 | user_tags Bitmap、users、events | audit_log（理由） | 一致；來源條件（從漏斗／路徑／歸因／留存下鑽）已在 v0.4.1 補上 |
| 標籤與分群 | events、users、items | user_tags（版本 7）、segments、dmp.tag_updates | 一致 |
| 即時觸發／推送 | Kafka 事件流、segments Bitmap | Webhook、Kafka、GCS、deliveries | 推送權限漏洞已修 |
| AI 洞察 | 語意層 → 同一編譯器 | insights、audit_log | 一致；工具目錄現在會隨元事件上線自動增加事件 |
| 權限中心 | 角色、指派、範圍 | 每次查詢的 WHERE 與遮罩 | 指派與模擬已補 |

## 3. 產品每個模組待確認細節（需客戶／PO 決定）

| 模組 | 待確認 | 建議預設 |
|---|---|---|
| 元事件管理 | 事件命名以客戶神策清單（112 個）為準，是否保留 `$` 預置事件原名；隔離區自動丟棄天數；變更單審批人（資料治理 vs 業務負責人） | 保留原名、CDC 補充事件以業務語意命名；30 天；資料治理＋事件負責人雙簽 |
| 屬性字典 | 數值屬性預設分桶規則；枚舉值新增是否需審批；L3 代碼化金鑰輪替週期 | 四分位自動分桶；枚舉新增不審批但通知；年輪替 |
| 用戶表 | 覆蓋率低於多少要在分析頁提示；標籤型屬性是否允許手動覆寫；DSAR 完成時限與證明格式 | 70%；不允許；30 天、PDF 報告 |
| OneID | 同手機多客戶（預設不改綁、人工）；登入改寫視窗（預設近 7 天匿名事件改寫到登入客戶，event time）；人工合併的審批人；GA `user_id` 代碼化是否通過法遵（docs/20） | 不改綁；7 天；資訊管理發起、系統管理員審批（docs/19）；HMAC 代碼送法遵 |
| 維度表與字典 | 商品主檔來源（交易所檔 vs 行內主檔）；組織樹變動對歷史事件的歸屬口徑（當前 vs 事件當下）；帳戶維度表 180 萬列用 dictGet 的記憶體（約 1 GB） | 行內主檔；預設「當前歸屬」，報表可切換；接受 |
| 數據整合 | 數據中台提供交易事實表的方式（Trino／Hive 批次 vs Kafka）與增量欄位；導入頻率（15 分鐘？）；GA360 匯出專案授權方式（WI vs SA 模擬）；模型清單與血緣要不要接 OpenLineage | CDC；WI；OpenLineage（M3） |
| 數據權限 | 五種角色皆全域：行銷是否需要分群限制（只看活動曝光者）；外包帳號回溯天數；K 匿名門檻（20？）適用於哪些模組 | 不限制；180 天；K=20，全模組分組結果 |
| 角色權限 | 五種角色（系統管理員、行銷、數據分析、數位經營、資訊管理）的審批分工是否如 docs/10 §6；行銷能否看用戶列表（隱碼）；臨時提權審批人 | 如 docs/10；可看隱碼列表、不可細查；系統管理員＋數位經營雙人 |
| 事件分析 | 自訂日期區間與相對時間；公式指標；多選值的 UI | 正式版 M2 |
| 漏斗 | 窗口上限（3650 天？）；關聯屬性的實作成本（arrayJoin）；流失用戶後續路徑是否自動帶入路徑分析 | 365 天；M3；是 |
| 留存 | 初始行為時間預設範圍（30 天只有 4 週 cohort）；區間留存口徑是否公開給客戶 | 預設 90 天；公開 |
| 行為路徑 | 預設抽樣比例；全量查詢是否需審批；節點拆分屬性上限 | 1/10；不審批但警示；每事件 1 個屬性 |
| 歸因 | 觸點定義誰維護（行銷 vs 數據）；回溯窗口改變是否重算觸點表（成本）；歸因價值用手續費還是毛利 | 行銷提、數據審；重算（夜間）；手續費 |
| 用戶列表 | 匯出上限（10 萬列）與浮水印格式；細查理由是否需主管事後抽查 | 10 萬；每月抽查 5% |
| 標籤與分群 | 標籤數上限（500）；標籤值版本保留（7）；分群審批人 | 500；7；數位經營 |
| 推送 | Webhook 目的地的網路白名單；名單是否附帶標籤（L2 區間化） | 固定出口 IP；預設附 lifecycle／tier |
| AI 洞察 | 第一階段是否啟用；LLM 閘道供應商；agent 可用工具範圍 | 第二階段；企業閘道；只讀工具 |
| 資料流與效能 | SLA 數值（即時 < 10 s、日批 < 07:00、各查詢 P95）；告警通知管道 | 如原型；Grafana → 值班群組 |
| 部署 | 正式 A 檔 6 台 vs D 檔 3 台；測試環境規模；機房 vs GCP | A／C-經濟；GCP |

## 4. 驗證

- Playwright：桌機 1440 與手機 390 跑過元事件管理（隔離事件登記、L4 攔截、新事件登記、屬性字典、虛擬事件）、用戶表、維度表與字典、資料流與效能三頁、權限中心指派與模擬；無 console error、無橫向溢出。
- 權限：以數據分析與行銷身分確認「登記事件」「核准」按鈕不出現、行銷不可細查；以系統管理員確認可操作。
- 契約：openapi.yaml 可解析；semantic/dimension_tables.yaml、oneid_rules.yaml、user_properties.yaml 可解析；auth.py、attribution.py 自測通過。
