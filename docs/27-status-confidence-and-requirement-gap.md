## 2. 信心度

| 面向 | 信心 | 依據與保留 |
|---|---|---|
| 分析查詢的**正確性**（事件／漏斗／留存／路徑／歸因／用戶） | 高 | 80 條黃金查詢由獨立 Python oracle 逐列比對，ClickHouse 25.8 LTS 與 26.10 都是誤差 0；36 條越權／越預算查詢全被拒。保留：測試資料是合成的，事件只有 6 種、用戶數萬級，真實字典（112 個事件）尚未跑過。 |
| **權限與遮罩** | 高 | 行級、欄位、K 匿名、匯出上限、揭露時效都有自動化測試，且是 SQL 層注入不是前端隱藏。保留：真實 AD／Entra ID 尚未接過，只接過假 IdP。 |
| **ClickHouse 規模**（7 億事件／月、500–650 萬 MAU） | 中 | 已量測 200 萬用戶 × 300 屬性與 1,000 萬事件（docs/23 §3）；10 億級基準（docs/09）尚未在正式規格機器上跑。路徑與歸因是視窗函數，在大期間要靠抽樣與預算限制，未在億級驗證。 |
| **資料接入**（GA360 BigQuery 匯出、神策歷史、數據中台交易） | 中偏低 | 管線與對帳邏輯有端到端測試，但都是合成資料；GA360 真實匯出 schema、神策 70 億筆歷史導出、數據中台寬表都還沒碰到真資料。這是上線風險最大的一塊。 |
| **前端** | 中 | 十個正式頁 typecheck／31 個單元測試／build 綠、桌機與手機截圖無溢出；但還沒有對真後端的瀏覽器端到端測試，八個模組仍是占位頁。 |
| **營運**（SLA、監控、告警、備援） | 低 | 只有 Helm 與 Keeper 部署腳本，沒有監控告警規則、備份演練、容量告警。 |

## 3. 測試情況

- **後端自測**（每次 CI）：policy、transforms、auth、oneid、api、segments、store_pg、modeling、scheduler、sensors_api 共 10 組，含必拒案例。
- **語意編譯器黃金測試**：80 條（事件 31、漏斗 9、留存 8、路徑 8、歸因 6、用戶 18）＋ 36 條必拒，oracle 逐列比對，`EXPLAIN ESTIMATE` 掃描列數上限檢查。
- **端到端**（真 ClickHouse 25.8 單一執行檔，CI 每次跑）：神策格式檔匯入 20 萬行 → GA4 匯出微批 → 數據中台訂單 → 用戶表 200 萬 × 300 屬性基準 → 編譯器 → REST → 分群 → 匯出。
- **前端**：vitest 31 個（規則建構器、桑基、系列、漏斗／留存／歸因純函式、API 客戶端、權限）；Playwright 只做截圖檢查（對假 API），無斷言型端到端。
- **安全與授權**：Trivy（映像＋依賴）、hadolint、gitleaks、OpenAPI 驗證、授權白名單（`LICENSES.md`）每次 CI。
- **沒有做的**：真資料、真 IdP、億級壓測、60 人併發、瀏覽器端到端、災難復原演練、滲透測試。

## 4. 專案難點

1. **線上行為資料要回地端合併**（需求 D1／D2／D3，客戶標示本案重點）。GA360 的資料在 Google Cloud（BigQuery），線下資料不得出境也不得上公有雲，所以合併只能發生在地端：BigQuery 匯出 → 地端 ClickHouse。要決定 BigQuery 的資料位置（台灣區）、匯出頻率（串流分鐘級或日批）、頻寬與費用（每月 7 億筆明細），以及 GA 端 user_id 只放去識別化 UUID。這也是客戶在 C1 寫「待討論是在 360、還是 DMP 中台、或丟去 CDP」的根本原因，需要一張兩方（Merkle／Data-DI）都簽字的資料流圖。
2. **三條 ID 要對得上**：GA 的 client_id／app_instance_id、客戶去識別化 UUID（人）與帳戶（一人多帳戶）、現有 CDP 的 ID。B3 客戶已標「需客製開發」；OneID 設計已有，但對照鑰匙由客戶持有，我們只能看到雜湊值，歸戶規則要和 Merkle 的埋點（登入即 set user_id）綁死。
3. **神策歷史 70 億筆導出與對帳**：客戶私有化神策，要從 Impala／HDFS 導出、轉名、三方對帳；API 直連連接器因 API Secret 是專案層而非 open-api 層尚未打通。這塊時程取決於客戶給的存取方式，不在我們手上。
4. **即時性與觸發**（C11、E2、S6）：第一階段是微批（5–15 分鐘），秒級觸發明確延後，且 MA 發送由客戶 MA 執行，我們只提供分群增量與 Webhook。要在回覆裡講清楚，避免客戶把「行為觸發行銷」算在我們頭上。
5. **儀表板**（C9，必要）：已做（存查詢條件、檢視者重算、分享）；尚缺拖曳排版與定時寄送。
6. **規模驗證**：7 億筆／月、500–650 萬 MAU 的硬體規格要靠 10 億級基準才敢給數字，需要一台正式規格的測試機（docs/13 的容量表目前是推算）。
7. **團隊**：沒有 ClickHouse 調優與維運專家（docs/23 §6 的對策是微批＋固定樣板），SLA／告警（G2）要另外找維運方或納入 Merkle 分工。

## 5. 需求確認表逐列比對（建議填入 M 欄「Data-DI 補充」）

落差欄位：**符合** = 現況已實作；**規劃中** = 契約／設計有、第一階段排程內；**落差** = 需求與規劃不一致或未規劃；**非本方** = 由 GA360／Merkle 負責。

| 編號 | 需求項目 | 落差 | M 欄建議文字 |
|---|---|---|---|
| A1 | Web／App 全埋點與自訂事件 | 非本方 | 採集由 GA360／Firebase SDK（Merkle）負責；DMP 承接 GA360 BigQuery 匯出的事件與屬性，並沿用既有 112 個事件字典做橋接轉名（docs/20、migration/bridge）。DMP 契約另有 `/v1/events` 直送口（給無法經 GA 的來源），第一階段排程內實作。 |
| A2 | Server-side／API 事件寫入 | 符合（批次已有、API 規劃中） | 線下事件（成交、開戶完成、調額）由數據中台批次匯入已實作，與線上行為以同一個 one_id 併入同一時間軸（有端到端測試）；`/v1/events` 批次寫入 API（去重、隔離區、審計）契約已定、第一階段排程內。建議線下事件走批次而非 API，以免交易系統多一個即時依賴。 |
| A3 | SDK 對 App 效能的影響 | 非本方 | GA／Firebase SDK 由 Merkle 回覆；DMP 不在 App 內植入任何元件。 |
| A4 | 推播、EDM、SMS 與 Deeplink 追蹤 | 非本方／部分 | 送達、開啟、短鏈點擊事件由 GA／推播工具產生並經 GA 匯出進 DMP；DMP 端以發送計畫 ID 作為事件屬性做漏斗與歸因（已支援關聯屬性）。延遲深層連結不斷軌屬 SDK 能力，由 Merkle 回覆。 |
| A5 | 渠道與 UTM 解析 | 符合（第一階段簡化） | 語意層支援虛擬屬性（欄位運算與 CASE，例如由網址判斷開戶來源），在元事件管理設定不需寫 SQL；GA 的 UTM 欄位匯入後直接是維度。進階表達式第二階段。 |
| A6 | 既有事件與歷史資料移轉 | 符合（設計與工具有，真資料未跑） | 神策 → GA360 埋點銜接表（`ga360_tracking_spec.csv`）、橋接轉名、導出任務狀態機與三方對帳已實作（docs/22）；近一年歷史由神策私有化環境導出後載入地端 ClickHouse。平行運行期雙寫方案：神策與 GA 同時埋點，DMP 兩邊都收，按日對帳。70 億筆歷史的導出取決於客戶提供 Impala／HDFS 或 API 存取（目前 API 直連尚待專案層金鑰）。 |
| A7 | 資料量與效能 | 規劃中（已有部分量測） | 已實測 200 萬用戶 × 300 屬性、1,000 萬事件（docs/23 §3）；7 億筆／月與 500–650 萬 MAU 的硬體規格依 docs/13 容量表推算（ClickHouse 3 節點起），正式數字要在正式規格測試機跑 10 億級基準後給。查詢回應：事件分析日聚合 < 1 s，明細層依期間長短 1–10 s，路徑／歸因大期間走抽樣。 |
